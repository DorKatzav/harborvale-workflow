ברוך הבא ל-HarborVale: כל מה שצריך כדי להתחיל לעבוד

הדף הזה כתוב בשבילך, השותף החדש בפרויקט. הוא אומר מה הפרויקט, איפה הכל נמצא, איך מקימים את הסביבה בעשר דקות, איך אנחנו עובדים (יש לנו פרוטוקול קבוע, והוא לא אופציונלי), ואיזה חלק מהעבודה מוצע לך. בסוף יש רשימת הצעדים שדור עושה כדי לצרף אותך.

01מה הפרויקט

הסיפור: Harbor & Vale היא חברת ריטייל-טק. צוות האנליסטים ניקה דאטה ושינה עמודה מסנטים לדולרים; מודל הנטישה של מדעני הנתונים התאמן על הקובץ החדש בלי שגיאה וסימן במשך חמישה שבועות את הלקוחות הטובים כ"בטוחים" ואת הגרועים כ"בסיכון". תקציב השימור הלך לאנשים הלא נכונים. הבעיה לא הייתה באף צוות: לא היה שום דבר ביניהם.

מה בונים: CrewAI Flow שמתאם שני צוותי סוכנים. צוות 1 (אנליסטים, 3 סוכנים) מנקה דאטה, עושה EDA, וכותב dataset_contract.json: חוזה שמתאר איך הדאטה הנקי אמור להיראות. צוות 2 (מדעני נתונים, 3 סוכנים) קורא רק את החוזה ואת הקובץ הנקי, בונה פיצ'רים, מאמן ומשווה מודלים, וכותב כרטיס מודל. ה-Flow מאמת את החוזה מול הדאטה לפני שצוות 2 רץ, רושם הכל, שומר כל תוצר בריפו, ועוצר עם הודעה קריאה כשמשהו לא מסתדר. ואז יש אתר Flask ב-Railway עם לוח "שבור את זה": משנים יחידה, וה-Flow מסרב לאמן.

הדאטה: E-commerce Customer Churn מ-Kaggle, כ-5,630 לקוחות, 20 עמודות, תווית נטישה, ריקים אמיתיים, ואיותים לא עקביים לניקוי.

03הקמת סביבה (כעשר דקות)

git clone https://github.com/DorKatzav/harborvale-workflow.git
cd harborvale-workflow
conda create -n harborvale python=3.11
conda activate harborvale
pip install -r requirements.txt          # הכל מוצמד; CrewAI 1.15.20, pandas 3.0.5, scikit-learn 1.9.0
cp .env.example .env                     # ואז לערוך: OPENAI_API_KEY שלך, LIVE_URL כמו למעלה
pytest && ruff check .                   # חייב להיות ירוק לפני שנוגעים בכלום
python scripts/gate.py --m 0             # שער התחנה האחרונה שנסגרה: PASS 5/5
flask --app app.main run                 # http://127.0.0.1:5000/health

שלושה דברים שלא עושים

  • לא מדביקים מפתחות ב-.env.example (הוא ב-git). רק ב-.env. השער סורק סודות לפני כל push, ואם הוא נכשל, לא דוחפים.
  • לא עובדים בסביבת פייתון אחרת. harborvale בלבד, ו-python ולא python3 (במק python3 עלול להצביע לפייתון של המערכת).
  • לא נוגעים ב-final_projec.html וב-data/raw/.

04איך אנחנו עובדים

הפרוטוקול קבוע ואותו דבר לכל תחנה. הוא נראה ביורוקרטי ביום הראשון, ומשלם את עצמו בשני: כל תחנה שנסגרה היא נקודה שאפשר לחזור אליה, לקרוא מה קרה, ולהמשיך.

  1. ענף לכל תחנה: git checkout -b feat/m<N>-<slug> מ-main מעודכן. אף פעם לא push ישיר ל-main.
  2. בדיקות ליד הקוד. כל מודול ב-hv/ נכתב עם בדיקות pytest. קומיטים קטנים עם feat: / test: / docs: / fix:.
  3. שער: python scripts/gate.py --m N חייב להדפיס GATE M<N>: PASS k/k. הבדיקות של כל שער כתובות ב-PLAN.md §4. מתקנים, לא מדלגים.
  4. דוח תחנה ב-docs/reports/M<N>_HE.html: מה נבנה, תוצאת השער, מה למדנו, מה הבא. עם צילומי מסך כשיש UI.
  5. יומן: רשומה ב-PROJECT_LOG.md. כל הפתעה בדאטה או שינוי מהתוכנית = החלטה מסומנת D-M<N>-<n> עם חלופות ומחיר. אף פעם לא "תיקון שקט".
  6. PR: gh pr create, CI ירוק (ruff + pytest; ה-CI לא קורא ל-OpenAI אף פעם), השותף השני קורא את הדוח ומאשר את המיזוג. אחרי המיזוג בודקים ש-Railway פרס ו-/health מחזיר את ה-commit החדש.
  7. דוחות ויומן נכנסים ב-PR נפרד (docs/m<N>-report) אחרי ה-PR של הקוד.

עם Claude Code

שנינו עובדים עם Claude Code. CLAUDE.md בשורש הריפו הוא ההסכם שהוא קורא בתחילת כל סשן: הפרוטוקול, כללי הברזל, מקורות האמת, הסביבה, ולקחים שכבר שולמו. אם אתה מתחיל סשן חדש, מספיק להגיד לו "קרא את CLAUDE.md ואת סוף PROJECT_LOG.md ותגיד לי איפה אנחנו". הוא בונה רק את התחנה הנוכחית, לא רץ קדימה, ולא מוסיף פיצ'רים שלא ביקשו. אם משהו ב-CLAUDE.md לא מתאים לך (למשל שפת הדוחות), זה שינוי של שורה ומדברים עליו.

כללי ברזל של הפרויקט (מ-CLAUDE.md, בקצרה)

  • החוזה הוא קובץ. צוות 2 מניח רק את dataset_contract.json ואת clean_data.csv. הכלי שלו מסרב לכל נתיב אחר, וזה נבדק.
  • שדות נמדדים מהכלי, טקסט מהסוכן. הסוכן רשאי לכתוב רק description, rationale, assumptions. המאמת מתעלם מהטקסט.
  • סוכנים לא מחשבים. כל ניקוי, סטטיסטיקה ואימון הם פונקציות ב-hv/ עם seed 42. הסוכנים מנצחים על התהליך וכותבים פרוזה.
  • קבצי הדאטה זהים בייט-בייט בין ריצות. זו בדיקת שער.
  • כל מספר בדוח מגיע מקובץ שנמדד (stats.json, metrics.json). אף אחד לא מקליד מספרים, גם לא סוכן.
  • כישלון = עצירה. FAILED.md, קוד יציאה 2, בלי ניסיון חוזר אוטומטי.
  • ריקים נשמרים ומוצהרים בחוזה; ההשלמה בתוך ה-Pipeline של המודל. Gender ו-MaritalStatus לעולם לא פיצ'רים.
  • מדווחים תוצאות כמו שהן, גם כשהן לא מחמיאות.

05איפה אנחנו ומה מוצע לך

M0 סגורה (ריפו, סביבה, Flask, CI, Railway, שער 5/5). כל השאר פתוח. ההצעה לחלוקה מתבססת על זה ש-PLAN.md §3 קובע את הממשקים מראש, אז שני אנשים יכולים לבנות במקביל בלי לדרוך אחד על השני:

מסלול A: צוות 1

  • M1 — כלי צוות 1: טעינה, ניקוי (מפת ישויות, כפילויות, טיפוסים), EDA עם דוח HTML.
  • M3 — צוות 1 ב-CrewAI: שלושה סוכנים, YAML, כלים, ריצה אמיתית.

מסלול B: החוזה וצוות 2

  • M2 — החוזה והמאמת: תשע בדיקות, שש תקלות מוכנות, break_it.py.
  • M4 — כלי צוות 2: פיצ'רים, שלוש וריאציות מודל, הערכה, כרטיס מודל. תלוי רק בפורמט החוזה מ-M2, לא בסוכנים.

M5 (ה-Flow) מחבר את שני החצאים, ונעשה יחד. אחר כך אחד לוקח את האתר (M6, M7) והשני את הביקורת האדברסרית ואת הסגירה (M8). מי לוקח איזה מסלול: לפי מה שמעניין אותך יותר, סוכנים ופרוזה (A) או אימות ומודלים (B). דור מתחיל את M1, אז אם לא סוכם אחרת, מסלול B פתוח.

לפני שנוגעים בקוד של תחנה

קוראים את התחנה ב-PLAN.md §4 (משימות, שער, סימני כשל) ואת החוזים הרלוונטיים ב-§3. אם משהו בחוזה לא מסתדר עם מה שאתה מגלה בדאטה, זה לא "משנים ומתקדמים" אלא החלטה D-M<N>-<n> ביומן, כי הצד השני בונה על אותו חוזה.

06מה דור עושה כדי לצרף אותך

  1. מוסיף אותך כ-collaborator בריפו (Settings → Collaborators, או gh repo add-collaborator).
  2. מפעיל הגנה על main (Settings → Branches → Branch protection: require a pull request, require status checks "test"). מהרגע הזה אף אחד לא דוחף ישירות ל-main, כולל דור.
  3. מעדכן ב-CLAUDE.md: שני אנשים, מי מאשר מיזוגים (הצד השני), ואת חלוקת המסלולים. שורה או שתיים.
  4. אופציונלי: מעביר את פתקי האובסידיאן של הפרויקט לתוך הריפו (notes/), כדי שיהיה מחברת משותפת שנוסעת עם הקוד. עד אז, היומן המשותף הוא PROJECT_LOG.md והדוחות ב-docs/reports/.
  5. שולח לך את הדף הזה, את הקישור לריפו, ואת ההודעה: "תריץ את סעיף 03, תגיד לי שהשער עבר, ותבחר מסלול".
